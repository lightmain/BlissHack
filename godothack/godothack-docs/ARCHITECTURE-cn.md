# 架构

GodotHack 是一个现代化 NetHack 项目，由两个协作的应用组成：

- 一个经过修改的 NetHack 后端，负责维护权威游戏状态和游戏规则。
- 一个 Godot 前端，负责渲染玩家体验，并向后端发送玩家意图。

两端通过承载 JSON 消息的 TCP session 通信。

## 目标

- 保留 NetHack 的游戏逻辑和行为，让它作为权威后端。
- 在 Godot 中构建更丰富的现代 UI，而不是用 GDScript 从头重新实现 NetHack 规则。
- 让前后端协议足够明确，使 AI agent 能安全地同时修改两端。
- 保持上游 NetHack 源码树易于识别，让后续合并上游更新仍然可行。

## 仓库形态

仓库在根目录保留原始 NetHack 源码树。GodotHack 在它周围新增项目专属内容：

```text
godothack/godothack-client/   Godot 客户端项目
godothack/godothack-docs/     GodotHack 专属文档、协议说明和 AI 指南
godothack/godothack-webclient 早期尝试的网页前端（而非Godot前端）暂时不使用
external/           后端使用的第三方依赖
doc/                上游 NetHack 文档
src/, include/, ... 上游 NetHack 后端源码树
```

## 后端

后端应该继续负责：

- 游戏规则和状态转换。
- 随机性、地牢生成、怪物、物品、回合和存档。
- 将游戏状态变化转换成协议事件发送给客户端。
- 在应用玩家命令之前校验传入命令。

优先把 NetHack 专属行为保留在现有 NetHack 模块中，并把 GodotHack 的传输/session 代码放在命名清晰的集成模块里。

## 前端

Godot 客户端应该继续负责：

- 渲染地图、实体、物品栏、消息、菜单和 UI 状态。
- 捕获玩家输入，并转换成协议命令。
- 只维护表现层所需的客户端状态。
- 处理连接生命周期、重连体验和协议错误展示。

客户端不应该变成第二套 NetHack 规则实现。

## 协议边界

TCP JSON 协议是两端之间的契约。参考 `PROTOCOL.md`。

协议变更应该谨慎进行。一次完整的协议变更通常需要更新：

- 后端消息序列化/解析。
- Godot 客户端消息序列化/解析。
- `PROTOCOL.md`。
- 测试或手动验证记录。


## 输入桥接层与 0.1 边界

GodotHack 采用加强版方案二。客户端发送协议层输入事件；后端维护活动提示、校验每个回答，并把已校验输入转换后交给 NetHack 原版核心或测试核心。

NetHack 桥接层应位于命名清晰的集成代码中，并紧邻 NetHack 输入接口和窗口接口回调。测试核心必须复用同一输入调度层和消息契约。这样 Godot 客户端不会出现第二个命令解释器。

后端生成不透明的提示标识和菜单项标识；客户端用它们回答提示和选择菜单项。菜单快捷键只是一种显示提示。

0.1 的强制输入、输出、消息顺序、验收流程和排除项由 MVP-0.1-cn.md 定义。

## NetHack 窗口端口桥接与地图渲染

窗口端口是 NetHack 在正常游戏过程中与面向玩家的用户界面交互的主要接口。
`include/winprocs.h` 定义了该接口的 `window_procs` 函数表。函数表覆盖逻辑窗口的
创建和销毁、文本输出、地图图形输出、菜单、状态栏更新、背包更新，以及按键、地图
坐标、确认回答、文本和菜单选择等玩家输入。

GodotHack 后端 TCP 适配层实现当前选用的窗口端口。NetHack 原版核心会在后端进程内
直接调用这些后端函数：

- 输出回调将相应内容序列化为 JSON 输出消息。
- 输入回调发送带类型的输入请求，等待匹配的 JSON 响应，校验响应，并返回 NetHack
  原版核心所需的值。

后端构建启用的每个函数表字段都必须有可调用的实现。MVP 可以为低优先级能力定义
明确的空操作或最小行为；但 0.1 支持的游戏流程能够调用到的每种输入能力，都必须
得到正确实现。

窗口端口是主要的用户界面边界，不是封闭 NetHack 全部内部数据的严格边界。当图形化
功能需要标准窗口端口回调没有提供的信息时，后端可以增加小型、命名清晰的
GodotHack 集成代码。这些代码必须遵守游戏中的玩家知识规则，不能把未见怪物、未发现
陷阱或其他隐藏状态发送给前端。

### 输入所有权与输入请求类型

NetHack 原版核心决定何时需要输入，以及此时需要哪一种输入。前端不能根据当前地图
或消息文本推断输入形式。因此，每个输入请求都必须包含明确的类型和不透明的请求
标识。输入类型包括命令按键、按键或地图坐标、确认回答、一行文本和菜单选择。前端
只能回答当前活动请求的请求标识。这样可以避免旧按键、地图点击或菜单选择被解释为
另一次内核请求的输入。

### 标准地图图形与丰富地图渲染

`print_glyph` 提供的是玩家可见的显示结果，不是某个地图格的完整游戏状态。它包含
前景 `glyph_info` 和背景 `glyph_info`。前景是 NetHack 按显示优先级处理后的当前主要
显示图形。背景是可选的、以地形为主的图形，供图形化窗口端口使用。它无法重建一个
格子中可能同时存在的全部独立状态，例如固定设施、刻字、已知陷阱、物品堆和生物。

上游图形窗口端口展示了两种不同的使用方式：

- Qt 端口接收前景和背景两个参数，但当前只保存和绘制前景图形；它只使用背景的格子
  边框颜色。因此，Qt 是窗口端口边界的有用参考，不是多层图块渲染的参考实现。
- `NetHackW.exe` 使用的 Windows 图形端口分别保存前景和背景图形。当存在可用背景图形
  时，它先绘制背景图块，再使用图块透明色绘制前景图块。这可以表现生物位于水、冰或
  熔岩之上的效果。

标准背景图形计算不会把每种固定设施都作为背景提供。特别地，英雄站在喷泉上时，背景
图形不会保留喷泉。内核仍然知道英雄位于喷泉，但普通 `print_glyph` 结果可以只包含
英雄这一主要图形，而没有喷泉背景图形。

GodotHack 有两个不同层级的地图渲染方式：

- 若目标是忠实复现终端显示，消费标准窗口端口输出的地图图形。
- 若目标是丰富的多层渲染，增加 GodotHack 专属的后端地图视图构造器。该构造器生成
  渲染器所需、且玩家当前可知的图层，例如地形、固定设施、刻字、已知陷阱、可见物品
  堆、生物和记忆状态。

丰富地图视图格式属于协议扩展。其准确消息结构由 `PROTOCOL.md` 定义；前端只能渲染
后端明确提供的信息。
