# GodotHack 0.1 最小纵向切片

本文档定义 GodotHack 0.1 的强制范围。0.1 的目标是证明一条完整、可测试的前后端链路，而不是实现完整 NetHack 界面。

本文档中的必须表示 0.1 验收条件；不包含表示实现不得以已经支持为前提。

## 目标

0.1 必须证明以下链路能够端到端工作：

1. Godot 客户端建立 TCP 连接并完成协议握手。
2. 客户端请求开始游戏。
3. 后端启动 NetHack 核心或测试核心。
4. 后端把核心输出转换为 JSON 视图和提示。
5. 客户端显示地图、玩家状态、消息、背包和提示。
6. 客户端回答当前提示。
7. 后端校验回答，交给当前核心，并发送新的视图和下一个提示。

0.1 不追求完整可通关流程。它追求后续扩展时不需要推翻输入边界、菜单身份和输出模型。

## 架构决定

采用加强版方案二。

- Godot 前端把玩家操作转换为协议输入，不转换为一串原生 NetHack 字符。
- 后端输入调度层持有当前提示，并校验每个输入。
- NetHack 桥接层在后端内部把已校验的输入转换为 NetHack 所需的输入回调。
- 测试核心桥接层消费同一种协议输入，产生同一种协议输出。
- 客户端不能直接声明任何游戏状态已经改变。

客户端必须使用后端发送的 prompt_id 回答提示，并使用 menu item id 选择菜单项。菜单显示中的 a-zA-Z 是临时快捷键，不能作为菜单项身份。

## 0.1 支持的客户端输入

### 会话输入

| 消息 | 是否必须 | 用途 |
|---|---|---|
| session.hello | 必须 | 协商协议版本并识别客户端。 |
| game.start | 必须 | 在当前会话创建一局新游戏。 |

0.1 不支持 game.resume、存档选择、旁观者、多个玩家或一个连接中的多个游戏会话。

### 单按键输入

input.key 只在 prompt.key 活动时可发送。0.1 的 Godot 界面必须提供以下键的可点击控件和键盘输入：

| 输入 | 含义 |
|---|---|
| h、j、k、l、y、u、b、n | 八方向移动，含斜向移动。 |
| . | 原地等待一回合。 |
| <、> | 在楼梯或梯子上上下层。 |
| s | 搜索。 |
| , | 拾取脚下物品。 |
| i | 请求查看背包。 |
| ESC | 取消当前允许取消的操作。 |
| ENTER | 确认或关闭允许确认的只读界面。 |
| SPACE | 继续允许翻页或继续的简单界面。 |

后端而不是 Godot 决定某个按键在当前状态是否有效、是否消耗回合、是否会打开下一层提示。

0.1 的 Godot 界面不必提供其他 NetHack 命令的专用按钮。后端也不得把未列入本表的按键宣称为已完成端到端支持。

### 菜单输入

input.menu_choice 必须支持单选、多选和取消。

菜单项至少包含稳定 menu item id、显示文本、可选状态、默认选中状态和可选的临时 accelerator。

客户端必须接收完整菜单项列表并自行提供滚动。0.1 不把服务器端的终端页码或 a-zA-Z 快捷键编码为菜单状态。

### 文本与短选项输入

input.text 必须用于玩家名称和测试核心要求的文本提示。客户端必须展示后端提供的默认文本、最大长度和是否允许空文本。

input.choice 必须用于有限选项提示，例如 y 或 n。客户端只能发送后端列出的 choice 值。

### 明确不包含的输入

0.1 不支持 Ctrl 组合键、Alt 或 Meta 组合键、数字小键盘模式、鼠标地图选点、自动旅行、扩展命令文本输入、方向前缀、数量前缀、命令重绑定、触屏手势和游戏手柄。

以后扩展这些功能时，必须新增明确的协议字段和验收条件，不能把平台物理键码悄悄塞入 0.1 的 input.key。

## 0.1 支持的后端输出

### 生命周期输出

后端必须发送 session.welcome、game.started、game.error 和 game.ended。

game.error 必须包含机器可读 code 和面向玩家的 message。至少支持 not_ready、unexpected_input、stale_prompt、invalid_choice、sequence_error 和 core_error。

### 地图输出

view.map 必须在启动后和每次接受输入后发送完整地图快照。

每个地图格必须包含：

| 字段 | 含义 |
|---|---|
| x、y | 从左上角开始的零基坐标。 |
| symbol | 一个最终显示字符。 |
| color | 后端给出的具名显示颜色。 |
| visibility | visible、remembered 或 unseen。 |

0.1 只传最终显示层。一个格子中隐藏的地形、怪物、陷阱和物品堆不单独发送。客户端不能依据 symbol 推断真实对象类型。

### 玩家状态输出

view.player 必须包含 name、role、dungeon_level、gold、hp、hp_max、pw、pw_max、armor_class、experience_level、turn 和 conditions。

后端不能用猜测值填充不可用统计；不可用值应为 null。

### 消息输出

view.messages 必须包含按时间顺序排列的消息行和 more_pending。后端保留最近 200 行，客户端显示该完整快照。

0.1 不支持消息分类、富文本、可点击链接、声音或动画事件。

### 背包输出

view.inventory 必须包含当前背包中每个可显示条目的 inventory_letter 和 text。

inventory_letter 只用于显示；客户端不得据此实现物品规则。text 是 0.1 的权威物品描述。0.1 不提供物品图标、重量、祝福或诅咒字段、装备槽结构、物品堆明细或容器树。

### 提示输出

后端任一时刻只能有一个活动提示，类型为：

| 提示 | 客户端回答 |
|---|---|
| prompt.key | input.key |
| prompt.menu | input.menu_choice |
| prompt.text | input.text |
| prompt.choice | input.choice |

提示被接受、取消或替换后，后端必须发送 prompt.closed。客户端只能关闭同一个 prompt_id 对应的界面。

## 视图与提示的发送顺序

后端接受一个输入后，必须按以下顺序发送消息：

1. 如果该输入回答了一个提示，发送该提示的 prompt.closed。
2. 发送最新 view.map。
3. 发送最新 view.player。
4. 发送最新 view.messages。
5. 发送最新 view.inventory。
6. 发送下一个活动提示。

若游戏结束，步骤 6 改为 game.ended。若核心无法继续，发送 game.error 后再发送 game.ended。

完整快照的顺序固定，使客户端无需猜测某个输入是否已经被处理。

## 必须演示的流程

测试核心必须实现下列确定性流程，用于客户端和协议的自动测试：

1. session.hello、session.welcome、game.start、game.started。
2. prompt.text 要求输入角色名称。
3. 输入名称后，发送地图、状态、消息、空背包和 prompt.key。
4. 输入一个方向键后，英雄位置变化，turn 增加，并发送新的完整快照。
5. 输入 , 后，发送至少含两个项目的多选 prompt.menu。
6. 选择其中一个项目后，背包快照出现该项目，消息说明拾取结果，随后回到 prompt.key。
7. 发送 prompt.choice，验证 y 与 n 两种回答及取消或错误处理。
8. 发送一个过期 prompt_id，后端返回 stale_prompt，游戏视图不变化。

NetHack 桥接层达到 0.1 时，至少必须完成同一套会话、快照和提示消息的连接。测试核心不是临时协议，它是协议一致性的自动测试实现。

## 验收标准

0.1 完成必须同时满足：

- Godot 客户端能连接测试核心并跑完上述流程。
- Godot 客户端能显示完整地图快照、状态、消息、背包、四种提示。
- 多选菜单可滚动、可保留已选项目，并提交稳定菜单项标识。
- 后端拒绝错误类型输入、旧提示输入和不属于当前菜单的项目。
- NetHack 桥接层与测试核心共用相同的 TCP JSON 消息结构。
- 协议、后端、Godot 客户端和测试验证在同一次改动中同步更新。

## 不应在 0.1 中提前实现的内容

不要在 0.1 中加入完整地图数据层、图块资源系统、动画、视野特效、完整物品检查界面、所有键位、菜单搜索、保存恢复、网络断线恢复、多会话、战斗日志分类或远程多人游戏。

这些内容都依赖本版本先稳定的提示状态、菜单身份和完整快照约定。
