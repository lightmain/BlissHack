# BlissHack 阶段四：长流程测试与导入事务保护设计

本文介绍 prealpha-2 阶段四准备实现的内容。本文假定读者学过基本的程序设计、
文件读写和自动化测试，但不假定读者熟悉 NetHack、WebAssembly、浏览器存储或
当前项目。文中会先说明现有程序怎样保存文件，再说明程序在哪些时刻可能丢失
数据，最后给出恢复方案和测试方案。

阶段四有两个直接目标。第一个目标是保护存档导入过程：页面在导入期间刷新、
关闭或者遇到写入错误之后，已有存档仍然可以恢复。第二个目标是重复执行新游戏、
继续游戏、保存、刷新、导出、删除和导入，以便发现只在多轮运行后出现的资源
泄漏、状态残留和存储错误。

## 1. 先理解当前程序怎样保存文件

### 1.1 WebAssembly 和游戏模块

WebAssembly 是浏览器可以执行的一种二进制程序格式。BlissHack 使用
Emscripten 把 NetHack 的 C 程序编译成 WebAssembly。Emscripten 是一套把
C 或 C++ 程序编译到浏览器环境的工具链，它还为编译后的程序提供文件系统等
运行能力。

浏览器使用 JavaScript 语言运行界面逻辑。BlissHack 的界面源码使用
TypeScript 编写；TypeScript 在 JavaScript 基础上增加编译时类型检查，构建
程序会把 TypeScript 转换为浏览器可以执行的 JavaScript。后文提到的
JavaScript 变量和 TypeScript 接口都属于这一层。

本文把 Emscripten 每次创建的一套完整运行环境称为“游戏模块”。一个游戏模块
包含一份 WebAssembly 程序实例、一块独立内存、一份独立的内存文件系统和一组
NetHack 全局变量。游戏模块在主界面出现前创建。玩家点击 New Game 或选择一个
存档之后，同一个游戏模块开始运行 NetHack。一个游戏模块最多运行一局游戏，
游戏结束后程序会丢弃旧游戏模块并创建新游戏模块。

本文把玩家从 New Game 或 Continue 开始，到 NetHack 正常退出并完成清理为止
的过程称为“游戏会话”。游戏模块和游戏会话的区别是：游戏模块在主界面出现前
已经存在，因为主界面需要使用游戏模块读取存档；游戏会话只在玩家决定开始或
继续游戏时创建。

例如，页面第一次打开时会创建游戏模块 M1。主界面使用 M1 读取存档。玩家点击
New Game 后，程序创建游戏会话 S1，S1 使用 M1 运行 NetHack。S1 结束后，程序
清理 M1，然后创建游戏模块 M2。此时主界面使用 M2 读取下一局可以选择的存档。

### 1.2 内存文件系统和持久化存储

WebAssembly 程序不能直接使用用户电脑上的普通文件路径。Emscripten 因此在
浏览器内存中提供一套文件系统。本文统一把这套文件系统称为“内存文件系统”。
NetHack 读取和写入的 `/save/0<角色名>` 位于内存文件系统中。

仅仅写入内存文件系统不能让文件跨页面刷新保留。页面刷新后，旧游戏模块和旧
内存都会消失。浏览器还提供名为 IndexedDB 的本地数据库接口，IndexedDB 中的
数据可以跨页面刷新保留。Emscripten 提供名为 IDBFS（IndexedDB File
System）的组件，用来在内存文件系统和 IndexedDB 之间复制文件。本文统一把
IndexedDB 中由 IDBFS 管理的数据称为“持久化存储”。

IDBFS 通过 `syncfs` 函数执行复制。本文统一把一次 `syncfs` 调用称为“存储
同步”。存储同步有两个方向：

1. `syncfs(true)` 从持久化存储读取文件，并把文件放入当前游戏模块的内存文件
   系统。程序在主界面显示存档列表之前执行这个方向的存储同步。
2. `syncfs(false)` 从当前游戏模块的内存文件系统读取文件，并把文件写入持久化
   存储。程序在保存、删除或导入之后执行这个方向的存储同步。

一个具体例子可以说明两个方向的区别。假设持久化存储中存在 Ada 的存档，页面
刷新后创建游戏模块 M2。M2 刚创建时的内存文件系统中还没有 Ada 的存档。M2
执行 `syncfs(true)` 后，Ada 的存档进入 M2 的内存文件系统，主界面才能列出
该存档。如果玩家随后删除 Ada 的存档，程序会先从内存文件系统删除文件，再
执行 `syncfs(false)`，从而把删除结果写入持久化存储。

### 1.3 正式存档文件和原始二进制存档

NetHack 正常保存后会生成一个二进制文件。本文统一把该文件的内容称为“原始
二进制存档”，把位于 `/save/0<角色名>` 的文件称为“正式存档文件”。例如，
角色名为 Ada 时，正式存档文件的路径是 `/save/0Ada`。

“二进制”表示文件内容由字节组成，文件内容没有转换成 JSON 文本，也没有添加
BlissHack 自己的外层格式。阶段四不会改变这个约定。导出的文件内容继续与正式
存档文件逐字节相同，导入成功后写入的内容也继续是原始二进制存档。

### 1.4 当前导入流程

当前实现收到一个待导入文件后，会先读取文件内容并检查文件是否属于当前
BlissHack 构建支持的存档格式。本文把这个检查过程称为“存档校验”，把执行
检查的函数称为“存档校验函数”。存档校验会检查由当前 C 程序生成的存档格式
指纹，还会读取角色名、职业、种族、性别和阵营。存档格式指纹是一组描述当前
程序版本、编译特征和关键数据结构尺寸的字节，用来拒绝明显不兼容的存档。

存档校验通过后，当前实现执行以下步骤：

1. 如果正式存档文件已经存在，程序把旧文件内容复制到内存中的变量。
2. 程序把新文件写到以 `.tmp` 结尾的临时路径。
3. 程序读回临时文件，检查读回内容是否与待导入内容逐字节相同。
4. 程序把临时文件改名为正式存档文件。
5. 程序执行 `syncfs(false)`。
6. 如果上述步骤抛出错误，程序尝试使用内存变量中的旧文件内容执行回滚。

本文把“发生错误后恢复操作开始前状态”的过程称为“回滚”。当前回滚可以处理
普通函数错误。例如，存储同步明确返回失败时，当前 JavaScript 代码仍在运行，
所以程序可以使用内存变量恢复旧文件。

页面刷新或页面关闭会销毁 JavaScript 变量，因此当前回滚不能处理页面中断。
假设旧正式存档文件内容为 A，待导入文件内容为 B。程序已经把正式存档文件
替换为 B，但是程序还没有完成存储同步。此时页面被刷新，保存 A 的内存变量
随页面一起消失。下一次启动只能看到持久化存储最终留下的文件，程序没有足够
信息判断应该保留 A 还是 B。阶段四首先解决这个问题。

## 2. 本文使用的固定术语

为了避免同一概念出现多个称呼，后文只使用下表中的名称。代码中的英文标识符
会保留，因为 TypeScript 源代码需要使用这些标识符；解释性文字仍使用中文名称。

| 名称 | 唯一含义 |
| --- | --- |
| 游戏模块 | Emscripten 一次创建的完整 WebAssembly 运行环境。 |
| 游戏会话 | 一次 New Game 或 Continue 开始后，到 NetHack 退出并完成清理为止的运行过程。 |
| 内存文件系统 | 当前游戏模块内存中的文件系统。 |
| 持久化存储 | IndexedDB 中由 IDBFS 管理、可以跨页面刷新保留的数据。 |
| 存储同步 | 使用 `syncfs` 在内存文件系统和持久化存储之间复制文件。 |
| 正式存档文件 | 路径为 `/save/0<角色名>`、可以由 NetHack 继续读取的文件。 |
| 待导入文件 | 用户通过浏览器文件选择器选择的文件。 |
| 临时文件 | 导入期间保存新内容、文件名以 `.tmp` 结尾的内部文件。 |
| 备份文件 | 导入期间保存旧正式存档内容、文件名以 `.bak` 结尾的内部文件。 |
| 事务记录文件 | 导入期间记录恢复所需状态、文件名以 `.journal` 结尾的内部文件。 |
| 存储操作 | 一次完整的初始化、扫描、同步、删除、导出、导入或恢复。 |
| 导入事务 | 从读取一个待导入文件开始，到导入完成、取消或失败为止的完整过程。 |
| 提交点 | 程序从此处开始承认新正式存档已经成功保存，并且以后不再恢复旧正式存档的时刻。 |
| 回滚 | 提交点之前发生错误时，恢复导入开始前文件状态的过程。 |
| 启动恢复 | 页面中断后，下一次页面启动时根据内部文件完成回滚或清理的过程。 |
| 故障注入 | 测试代码在指定步骤主动产生错误，用来验证错误处理。 |
| 过期回调 | 已经结束的游戏会话曾经注册的回调函数。 |
| 运行事件 | 记录游戏模块、游戏会话和存储操作状态变化的一条结构化记录。 |
| 测试接口 | 只在自动化测试构建中启用、用于读取内部状态或触发过期回调的接口。 |
| SHA-256 摘要 | 根据文件全部字节计算出的固定长度数值；相同字节会产生相同摘要，测试用它比较导入前后的文件。 |

回调函数是另一个需要提前说明的概念。NetHack 的 WebAssembly 程序需要通知
浏览器界面显示窗口、地图和输入问题，因此每个游戏会话会注册一个 JavaScript
函数，WebAssembly 程序在需要通知浏览器界面时调用该函数。本文把这种函数称为
“回调函数”。游戏会话结束后，回调函数应当失效。已经失效的回调函数就是表中
的过期回调。

## 3. 阶段四的范围

阶段四会增加以下能力：存储操作的串行执行和状态记录；每个导入事务的唯一
编号；临时文件、备份文件和事务记录文件；页面启动时的导入事务恢复；每个导入
步骤的故障注入；能够区分内存文件系统与持久化存储的单元测试工具；只在测试
构建中启用的测试接口；容量固定的内存运行事件记录；独立的长流程浏览器测试
命令；测试失败时保存的状态记录、浏览器错误、截图和执行记录。

阶段四不会修改 NetHack 的 C 游戏逻辑，不会修改原始二进制存档的格式，也不会
承诺修复任意损坏的存档。阶段四仍然只允许同一标签页运行一个游戏会话，也不会
解决多个标签页同时写入同一个持久化存储的问题。阶段五计划实现的完整致命错误
页面、跨刷新日志保存和日志下载也不在本阶段完成。

## 4. 必须一直成立的条件

下面的条件是设计和测试共同使用的判断标准。测试只验证界面最终看起来正常还
不够，因为旧游戏会话可能仍在后台持有回调函数，存储队列也可能仍有未结束的
写入。

1. 同一标签页中的活动游戏会话数量只能是零或一。主界面对应零，游戏界面对应
   一。
2. 一个游戏模块最多调用一次 NetHack 的 `main()` 函数。`main()` 是开始运行
   NetHack 主程序的入口。
3. 游戏会话结束后，程序必须删除该游戏会话注册的回调函数。测试即使保存了
   过期回调的引用，调用过期回调也不能改变当前游戏会话、地图或输入状态。
4. 同一个游戏模块中的存储操作必须按照开始顺序逐个执行。一个存储操作完成或
   完成回滚之后，下一个存储操作才能开始。
5. 程序开始游戏会话之前，必须等待当前主界面的存储操作和启动恢复全部结束。
6. 程序报告导入成功之前，正式存档文件必须可以读回，必须通过存档校验，并且
   必须已经写入持久化存储。
7. 提交点之前发生错误时，原来存在的正式存档文件必须恢复为原来的全部字节；
   原来没有正式存档文件时，回滚后也不能出现新的正式存档文件。
8. 提交点之后发生页面中断时，程序保留已经提交的新正式存档文件。下一次启动
   只删除导入遗留的内部文件。
9. 程序无法可靠判断应该回滚还是保留新文件时，程序停止后续写入并保留恢复所
   需文件。程序不能根据文件修改时间猜测。
10. 存档列表只显示正式存档文件，不能显示临时文件、备份文件或事务记录文件。
11. 错误和运行事件可以记录编号、步骤和数量，但不能记录角色名、存档路径、
    文件内容、游戏消息或按键。
12. 自动化测试结束时不能存在未完成的存储操作。测试可以在明确说明的情况下
    留下一个活动游戏会话，否则活动游戏会话数量必须为零。

## 5. 存储操作怎样串行执行

当前代码只保证多个存储同步逐个执行。阶段四需要扩大这个保护范围，因为一次
导入包含读取、写入、改名、校验、存储同步和重新扫描。如果程序只排列存储同步
的顺序，删除和导入仍然可能在两个存储同步之间交叉修改文件。

阶段四会增加“存储操作协调器”。存储操作协调器维护一个等待队列。等待队列是
按照进入顺序保存尚未执行任务的数据结构。任意时刻只有队列开头的一个存储操作
可以访问文件系统，其余存储操作等待。前一个存储操作发生错误时，存储操作
协调器会等待该操作完成回滚，然后才允许下一个存储操作开始。

每个存储操作都有一个“存储操作编号”。编号只由递增数字和随机字符组成，不
包含角色名。例如，编号可以是 `storage-op-12-a8f3`。每个导入事务另有一个
“导入事务编号”，例如 `import-4-b91c`。两个编号的用途不同：存储操作编号
指出哪一次函数执行失败，导入事务编号把文件读取、冲突确认、覆盖和恢复联系为
同一次导入。

假设玩家选择 Ada 的文件，程序发现同名存档并显示冲突确认框。读取和检查文件
是第一个存储操作。玩家点击 Overwrite 后，替换文件是第二个存储操作。两个
存储操作使用不同的存储操作编号，但使用同一个导入事务编号。玩家停留在冲突
确认框时，等待队列中没有正在执行的存储操作；游戏会话仍然不能开始，因为这个
导入事务还在等待用户决定。玩家点击 Cancel 后，程序清除该导入事务并允许开始
游戏会话。

存储操作协调器会提供一个只读状态，其中包含当前存储操作的种类、存储操作
编号、导入事务编号、当前步骤和等待数量。程序可以等待该状态变为空闲。长流程
测试也会读取该状态，以便在每轮结束时确认没有尚未结束的工作。

存储操作失败时，错误对象使用固定字段保存存储操作种类、存储操作编号、导入
事务编号、失败步骤和原始错误。错误对象是一组带有固定名称的值，程序和测试
可以直接读取这些值，无需分析错误文字。普通界面只显示简短错误说明；运行事件
和测试结果文件记录这些固定字段。任何一层重新抛出错误时都必须保留原编号，
以便开发者确认多层函数报告的是同一次存储操作。

## 6. 导入事务使用的三个内部文件

每个开始写入的导入事务使用三个内部文件，文件名中的 `<导入事务编号>` 不包含
角色名：

```text
/save/.blisshack-import-<导入事务编号>.tmp
/save/.blisshack-import-<导入事务编号>.bak
/save/.blisshack-import-<导入事务编号>.journal
```

临时文件保存待导入的新内容。备份文件保存导入开始前的旧正式存档内容；目标
位置原来没有正式存档文件时，不创建备份文件。事务记录文件保存启动恢复需要的
少量文字数据。

事务记录文件采用 JSON 格式。JSON 是一种使用字符串、数字、布尔值、数组和
对象表示结构化数据的文本格式。事务记录文件的 TypeScript 结构如下：

```ts
interface ImportJournalV1 {
  schemaVersion: 1;
  kind: "raw-save-import";
  transactionId: string;
  phase: "prepared" | "committed";
  destinationFileName: string;
  hadOriginal: boolean;
}
```

这些代码字段与本文术语的对应关系如下：`transactionId` 是导入事务编号；
`phase` 是恢复阶段；`destinationFileName` 是正式存档文件的文件名；
`hadOriginal` 表示导入开始前是否存在正式存档文件。`schemaVersion` 表示
事务记录文件结构的版本，启动恢复只接受当前明确支持的版本。

事务记录文件最大为 4096 字节。程序读取事务记录文件后会重新检查导入事务
编号和正式存档文件名是否合法，不能直接把文件中的路径交给文件系统。事务记录
文件不会保存待导入内容或旧存档内容。事务结束后，程序必须删除三个内部文件。
这些文件只用于恢复，不会成为长期存档索引。

阶段三的实现只把旧存档内容保存在 JavaScript 内存中。阶段四仍然保留这份内存
副本，因为普通错误发生后可以立即使用该副本；阶段四还会把同样的旧存档内容
写入备份文件并写入持久化存储，因为页面刷新后只能依靠备份文件恢复。

## 7. 一次正常导入的完整过程

下面使用一个完整例子说明正常导入。假设正式存档文件原来的内容是 A，玩家选择
的待导入文件内容是 B，而且玩家已经确认覆盖。A 和 B 表示两组完整字节，不
表示文件名。

### 7.1 读取和校验

程序先检查待导入文件的大小。空文件和超过 64 MiB 的文件会在读取前被拒绝。
MiB 是以 1024 × 1024 字节计算的容量单位。文件大小合法后，程序读取全部
字节，并调用存档校验函数检查 B。存档校验完成之前，程序不会创建临时文件、
备份文件或事务记录文件。

程序根据 B 内部的角色名计算正式存档文件名。浏览器文件选择器提供的上传文件
名不参与这个计算。例如，用户把文件改名为 `my-save.bin`，只要文件内部角色名
仍为 Ada，正式存档文件仍然是 `/save/0Ada`。

### 7.2 准备恢复材料

程序读取 A，把 A 保存在内存变量中，同时把 A 写入备份文件。程序把 B 写入
临时文件，然后读回临时文件并逐字节比较。读回内容与 B 完全相同时，程序写入
阶段为 `prepared` 的事务记录文件。本文把 `prepared` 称为“已准备阶段”。

程序随后执行第一次 `syncfs(false)`。第一次存储同步成功后，A 的备份文件、
B 的临时文件和已准备阶段的事务记录文件都进入持久化存储。此时正式存档文件
仍然保存 A。页面在这个时刻刷新时，下一次启动可以读取备份文件和事务记录
文件，并明确知道本次导入尚未提交。

### 7.3 替换并重新检查

第一次存储同步成功后，程序把临时文件改名为正式存档文件，所以内存文件系统中
的正式存档文件从 A 变成 B。程序执行第二次 `syncfs(false)`，把 B 写入持久化
存储。

第二次存储同步成功后，程序从正式存档文件读回 B，进行逐字节比较，再调用存档
校验函数。程序随后重新扫描存档列表，确认列表中恰好存在一个对应角色的有效
正式存档文件。重新扫描失败也算导入失败，因为界面此时无法证明刚写入的文件
能够作为有效存档使用。

虽然第二次存储同步已经把 B 写入持久化存储，导入事务此时仍处于已准备阶段。
页面此时刷新后，启动恢复会使用备份文件恢复 A。这样规定的原因是程序尚未到达
提交点，也尚未向玩家报告成功。

### 7.4 到达提交点

正式存档文件通过重新检查后，程序把事务记录文件的阶段改为 `committed`。
本文把 `committed` 称为“已提交阶段”。程序执行第三次 `syncfs(false)`。
已提交阶段的事务记录文件进入持久化存储的时刻就是提交点。正常情况下，第三次
存储同步成功返回，表示程序已经越过提交点。

提交点之后，持久化存储中同时存在有效的 B、A 的备份文件和已提交阶段的事务
记录文件。页面此时刷新后，启动恢复会保留 B 并删除内部文件。程序不会恢复 A，
因为已提交阶段明确记录了导入已经成功。

如果第三次存储同步返回错误，程序可能无法判断已提交阶段的事务记录文件是否
已经进入持久化存储。程序此时不显示导入成功，也不继续其他写操作，而是要求
执行启动恢复。启动恢复读到已准备阶段时恢复 A，读到已提交阶段时保留 B。两种
结果都保留一份经过校验的正式存档文件，启动恢复也会记录最终选择。

### 7.5 清理内部文件

程序删除临时文件、备份文件和事务记录文件，然后执行第四次
`syncfs(false)`。第四次存储同步把清理结果写入持久化存储。该存储同步成功
后，导入事务结束，程序向界面显示普通的导入成功提示。

第四次存储同步失败时，B 已经在提交点之前可靠写入。程序保留 B，并把当前状态
记录为“已提交但等待清理”。界面显示“存档已经保存，内部文件将在下次启动时
清理”，下一次页面启动会根据已提交阶段的事务记录文件删除内部文件。恢复 A
会让已经提交的结果发生反转，因此提交点之后不再执行回滚。

正常导入总共执行四次从内存文件系统到持久化存储的存储同步。导入是低频操作，
额外等待时间可以接受。四次存储同步分别保证恢复材料已经保存、新正式存档已经
保存、提交决定已经保存、内部文件已经清理。程序不依赖多个文件必须一次全部
成功写入的假设。

## 8. 普通错误怎样回滚

“普通错误”表示页面和 JavaScript 程序仍然运行，函数能够捕获错误，并且程序
可以确认导入尚未到达提交点。例如，写入临时文件失败、改名失败、第一次或
第二次存储同步返回失败以及重新扫描失败都属于普通错误。第三次存储同步返回
失败时可能无法确定提交决定是否已经进入持久化存储，因此按照第 7.4 节执行
启动恢复。

提交点之前发生普通错误时，程序执行以下步骤：

1. 如果事务记录文件已经存在，程序保证该文件仍然表示已准备阶段。
2. 导入前存在正式存档文件时，程序从内存副本恢复 A；内存副本不可用时，程序
   从备份文件读取 A。
3. 导入前不存在正式存档文件时，程序删除导入过程中可能出现的新正式存档
   文件。
4. 程序删除临时文件。
5. 程序执行一次存储同步，把恢复结果写入持久化存储。
6. 程序读回正式存档文件，确认内容与 A 逐字节相同。
7. 程序删除备份文件和事务记录文件，再执行一次存储同步。
8. 回滚全部完成后，程序向界面报告最初发生的错误。

回滚过程本身也可能失败。例如，浏览器的可用存储空间已经耗尽，恢复 A 后的
存储同步仍然失败。此时程序会同时保留最初错误和回滚错误，停止该游戏模块中的
后续写操作，并保留备份文件和事务记录文件。程序下一次启动时重新执行启动恢复。
如果启动恢复仍然无法完成，程序进入不可继续状态。阶段五会为这个状态提供完整
的致命错误页面；阶段四先保证程序不会继续写入并覆盖恢复材料。

## 9. 页面中断后怎样恢复

“页面中断”表示当前 JavaScript 代码来不及执行回滚，例如用户刷新页面、关闭
页面或浏览器进程终止。下一次页面启动会创建新游戏模块，先执行
`syncfs(true)`，然后在显示存档列表之前执行启动恢复。

启动恢复先扫描三个内部文件，并按导入事务编号把属于同一次导入的文件放在
一起。启动恢复根据事务记录文件中的阶段决定后续操作。

### 9.1 事务记录文件处于已准备阶段

已准备阶段表示导入没有到达提交点。导入前存在正式存档文件时，启动恢复读取
备份文件的全部字节，使用存档校验函数检查这些字节，然后把备份内容写回正式
存档文件。导入前不存在正式存档文件时，启动恢复删除导入过程中可能出现的正式
存档文件。启动恢复最后删除三个内部文件，执行存储同步，并重新检查结果。

继续使用前面的 A 和 B 例子：即使第二次存储同步已经把 B 写入持久化存储，只要
事务记录文件仍处于已准备阶段，启动恢复就会恢复 A。程序使用事务记录文件中的
明确阶段作出决定，不使用文件修改时间。

### 9.2 事务记录文件处于已提交阶段

已提交阶段表示程序已经越过提交点。启动恢复检查正式存档文件是否存在并通过
存档校验。检查成功时，启动恢复保留 B，删除临时文件、备份文件和事务记录
文件，然后执行存储同步。

正式存档文件缺失或校验失败时，启动恢复尝试校验备份文件。备份文件有效时，
启动恢复恢复 A，并报告导入提交后的数据损坏。正式存档文件和备份文件都无法
校验时，启动恢复保留现有文件并进入不可继续状态，因为程序此时没有可靠依据
选择一个文件。

### 9.3 缺少事务记录文件

页面可能在创建某个内部文件之后、写入事务记录文件之前中断，因此启动恢复还要
处理缺少事务记录文件的情况。

没有事务记录文件的临时文件不可能是正式存档文件，启动恢复可以删除该临时
文件。没有事务记录文件的备份文件需要先读取全部字节并调用存档校验函数。程序
可以从备份内容中的角色名计算对应的正式存档文件。正式存档文件缺失或校验失败
时，程序恢复备份文件；正式存档文件有效时，程序保留正式存档文件并删除孤立的
备份文件。

事务记录文件内容损坏、结构版本未知、正式存档文件名非法、同一个正式存档文件
对应多个未完成导入事务，或者备份文件与事务记录文件表示的角色不一致时，启动
恢复停止写入并进入不可继续状态。这些情况无法通过明确规则判断哪个文件正确。

### 9.4 不同中断位置的结果

下表继续使用旧内容 A 和新内容 B：

| 中断位置 | 持久化存储中可能存在的内容 | 下一次启动结果 |
| --- | --- | --- |
| 第一次存储同步之前 | 正式存档文件 A | 保留 A，删除可能出现的孤立临时文件。 |
| 第一次存储同步之后、替换之前 | A、备份 A、临时 B、已准备阶段记录 | 恢复或确认 A，删除内部文件。 |
| 替换之后、第二次存储同步完成之前 | A 或 B、备份 A、已准备阶段记录 | 使用备份恢复 A。 |
| 第二次存储同步之后、提交点之前 | B、备份 A、已准备阶段记录 | 使用备份恢复 A。 |
| 提交点之后、清理完成之前 | B、备份 A、已提交阶段记录 | 保留 B，删除内部文件。 |
| 第四次存储同步之后 | 正式存档文件 B | 不需要启动恢复。 |

## 10. 导入事务的状态

代码会使用一组固定状态描述导入事务。明确状态可以让测试验证每一步，也可以
防止程序从一个不允许的状态直接跳到成功。

| 状态 | 含义 | 是否写过正式存档文件 |
| --- | --- | --- |
| 已创建 | 已分配导入事务编号，尚未读取文件。 | 否 |
| 正在读取 | 正在读取待导入文件。 | 否 |
| 正在校验 | 正在检查待导入内容。 | 否 |
| 等待覆盖确认 | 已发现同名正式存档，正在等待用户选择。 | 否 |
| 正在准备 | 正在创建临时文件、备份文件和事务记录文件。 | 否 |
| 已准备 | 恢复材料已经写入持久化存储。 | 否 |
| 正在替换 | 正在把临时文件改名为正式存档文件。 | 可能 |
| 正在重新检查 | 正在读回正式存档文件并重新扫描。 | 是 |
| 正在提交 | 正在写入已提交阶段并执行第三次存储同步。 | 是 |
| 已提交 | 已经越过提交点。 | 是 |
| 正在清理 | 正在删除三个内部文件。 | 是 |
| 已完成 | 导入事务已经结束。 | 是 |
| 正在回滚 | 正在恢复导入开始前的文件状态。 | 可能 |
| 需要启动恢复 | 当前页面无法完成回滚，需要下一次启动继续。 | 可能 |

用户点击 Cancel 时，等待覆盖确认状态直接结束，程序不会写任何文件。用户点击
Overwrite 时，同一个导入事务从等待覆盖确认进入正在准备。游戏模块失效或
用户关闭存档列表时，程序必须清除尚未写文件的导入事务及其内存中的待导入
内容。

## 11. 怎样测试每一个失败位置

### 11.1 故障注入

自动化测试需要稳定地让指定步骤失败。等待浏览器偶然出现磁盘错误无法重复同一
问题，也无法覆盖全部步骤。阶段四会在存储代码的关键位置调用一个默认不做任何
事情的检查函数。单元测试可以替换该函数，让它在指定步骤抛出错误。这个方法
就是故障注入。

可注入错误的步骤使用以下固定名称：

| 步骤名称 | 发生位置 |
| --- | --- |
| 读取待导入文件 | 浏览器读取用户选择的文件时。 |
| 校验待导入内容 | 存档校验函数检查新内容时。 |
| 读取旧正式存档 | 程序准备内存副本和备份文件时。 |
| 写入临时文件 | 程序保存新内容时。 |
| 校验临时文件 | 程序读回并比较临时文件时。 |
| 替换正式存档 | 程序把临时文件改名时。 |
| 保存恢复材料 | 第一次存储同步时。 |
| 保存新正式存档 | 第二次存储同步时。 |
| 重新扫描存档 | 程序检查新正式存档时。 |
| 保存提交决定 | 第三次存储同步时。 |
| 清理内部文件 | 程序删除内部文件时。 |
| 保存清理结果 | 第四次存储同步时。 |
| 执行回滚 | 普通错误后的恢复过程中。 |
| 执行启动恢复 | 下一次页面启动的恢复过程中。 |

每个步骤至少测试“执行前立即失败”。会改变持久化存储的步骤还要测试“数据已经
写入，但函数随后报告失败”。后一种测试覆盖程序无法从函数返回值确定最终写入
结果的情况。

普通错误测试允许当前函数进入回滚。页面中断测试会抛出一种只供测试使用的特殊
错误，测试工具随后立即丢弃当前内存文件系统，不执行当前页面的回滚，再创建新
游戏模块并运行启动恢复。这样可以准确检查刷新后的行为。

### 11.2 区分内存文件系统和持久化存储

当前单元测试工具只保存一份文件集合，因此无法模拟“内存中已经改成 B，持久化
存储中仍然是 A”。阶段四会把测试工具扩展为两份独立文件集合：

- `memoryFiles` 表示当前游戏模块的内存文件系统；
- `persistedFiles` 表示最后一次成功存储同步后的持久化存储。

测试工具执行 `syncfs(true)` 时，把 `persistedFiles` 复制到
`memoryFiles`。测试工具成功执行 `syncfs(false)` 时，把 `memoryFiles`
复制到 `persistedFiles`。测试还可以让存储同步在复制前失败，或者先完成复制
再报告失败。

例如，测试可以先让两份集合都保存 A，然后在 `memoryFiles` 中写入 B，并让
第二次存储同步先复制 B 再报告错误。回滚完成后，测试必须检查两份集合都恢复
为 A。另一个测试会在相同位置模拟页面中断，丢弃 `memoryFiles`，从
`persistedFiles` 创建新游戏模块，再检查启动恢复是否恢复 A。

### 11.3 单元测试覆盖

Vitest 是本项目运行 TypeScript 单元测试的工具。阶段四会使用 Vitest 覆盖
下列内容：

1. 导入事务的每个合法状态转换和非法状态转换。
2. 上表每个故障注入步骤。
3. 覆盖已有正式存档时，提交点前的每个失败都恢复全部旧字节。
4. 导入新角色时，提交点前的每个失败都不留下正式存档文件。
5. 回滚写入失败和回滚存储同步失败。
6. 已准备阶段、已提交阶段、孤立临时文件和孤立备份文件的启动恢复。
7. 损坏的事务记录文件、未知结构版本、非法正式存档文件名和缺少备份文件。
8. 两个导入事务指向同一个正式存档文件时停止写入。
9. 一个存储操作失败后，等待队列中的下一个操作仍然按顺序执行。
10. 等待覆盖确认时拒绝开始游戏会话，Cancel 后恢复正常。
11. 每个测试结束时，存储操作协调器处于空闲状态。

## 12. 长流程浏览器测试

Playwright 是本项目控制真实 Chromium 浏览器的自动化测试工具。Chromium 是
Chrome 浏览器所基于的开源浏览器内核。Vitest 适合精确控制函数错误，
Playwright 适合验证真实的 WebAssembly、浏览器界面、IndexedDB、下载和文件
选择器能够一起工作。

阶段四增加独立命令：

```bash
cd frontend
npm run test:long
```

普通浏览器测试继续验证一次新游戏、保存、继续、导入和导出。长流程浏览器测试
重复相同流程，用来发现第二局以后才出现的问题。长流程测试使用独立的浏览器
存储环境、独立端口和独立测试结果目录，避免与普通浏览器测试共享存档。

测试不会使用固定时间等待。例如，测试不会写“等待两秒后继续”。测试会等待
可以验证的条件，例如主界面按钮出现、游戏会话数量变为零、存储操作协调器变为
空闲或者浏览器发出下载完成事件。这样可以减少机器速度差异造成的失败。

### 12.1 游戏会话生命周期重复 10 次

每一轮从主界面点击 New Game，等待名字输入，输入该测试使用的唯一名字，然后
等待随机角色选择问题。程序在这一阶段已经调用 NetHack 的 `main()`，已经完成
窗口初始化并创建游戏会话。测试按 `q` 使用项目已经支持的正常退出路径，然后
等待新主界面和新游戏模块准备完成。

每轮结束时，测试检查活动游戏会话数量为零、已注册回调函数数量为零、存储操作
协调器为空闲。测试记录每一轮的游戏模块编号和游戏会话编号，最后确认 10 个
游戏会话编号互不相同，相邻两轮使用不同游戏模块，而且任意观测时刻都没有两个
活动游戏会话。

第二轮运行时，测试还会调用第一轮保存的过期回调。调用前后，当前游戏会话
编号、浏览器显示的地图内容和输入状态必须保持不变，运行事件中必须增加一条
“忽略过期回调”的记录。

### 12.2 同一个存档继续和保存 10 次

测试先通过真实界面创建角色并保存一次。随后每一轮刷新页面，等待主界面的存储
操作完成，打开存档列表，确认目标角色只出现一次，然后点击 Continue。游戏
恢复后，测试确认名字输入和角色创建界面没有出现，并确认地图与角色状态可见。

测试随后通过 NetHack 的标准 `S` 命令、保存确认问题和 `--More--` 提示完成
保存。测试等待新主界面、新游戏模块和存储操作协调器全部准备完成，再检查存档
列表中仍然只有一个目标角色，并检查三个内部文件都不存在。这个过程重复 10
次，每轮必须使用新的游戏会话编号。

该测试不会要求角色移动。初始房间和相邻地形由随机地图生成，依赖某个方向可以
移动会让测试结果受随机地图影响。保存和继续本身已经覆盖阶段四关心的生命周期
与持久化行为。

### 12.3 导出、删除、导入和继续重复 5 次

测试从一个正式存档文件开始。每一轮先通过真实下载按钮导出文件，并使用 Node.js
标准库计算下载内容的 SHA-256 摘要。Node.js 是运行 Playwright 测试程序的
JavaScript 运行环境。测试完成二次删除确认，等待删除写入持久化存储，然后
通过真实文件选择器导入刚才下载的文件。

导入完成后，测试再次导出文件，比较两次文件的全部字节和 SHA-256 摘要。比较
成功可以证明导出、删除和导入没有修改原始二进制存档。测试随后检查正式存档
列表只有一个项目，三个内部文件都不存在，然后 Continue 并再次保存，为下一轮
生成正式存档文件。

SHA-256 摘要只在同一轮导出和导入之间比较。NetHack 继续游戏后再次保存时，
游戏时间和其他内部状态可能发生合法变化，因此不同轮次的正式存档文件不要求
产生相同摘要。

### 12.4 页面进入后台和重复扫描

测试在主界面记录当前游戏模块编号和活动游戏会话数量，然后在同一个浏览器存储
环境中打开第二个页面，使原页面失去焦点，再返回原页面。返回后，游戏模块编号
不能变化，活动游戏会话数量仍为零。测试不会仅仅手工发送一个伪造的页面事件，
因为伪造事件不能完整代表浏览器把页面放入后台的行为。

测试还会反复打开和关闭存档列表，并通过刷新页面触发新的游戏模块、从持久化
存储读取文件和重新扫描。每次扫描后，正式存档文件不能重复出现。测试结束时，
存储操作协调器必须空闲，三个内部文件都必须不存在。

## 13. 测试接口和运行事件

### 13.1 为什么需要测试接口

浏览器界面可以显示主界面或游戏界面，但界面不能直接证明后台只有一个游戏
会话，也不能证明存储操作协调器已经空闲。阶段四因此增加测试接口。测试接口
只在构建命令设置 `VITE_ENABLE_TEST_API=1` 时注册。公开部署的构建不会设置
这个值，所以公开页面中不存在测试接口。

测试接口可以读取以下信息：

- 当前应用处于加载、主界面、游戏界面还是错误界面；
- 当前游戏模块编号和游戏会话编号；
- 活动游戏会话数量；
- 已注册回调函数数量；
- 当前存储操作、当前步骤和等待数量；
- 正在等待覆盖确认的导入事务编号；
- 临时文件、备份文件和事务记录文件的总数；
- 最近的运行事件。

测试接口还提供一个专门方法，用于调用测试构建保留的过期回调。测试构建最多
保留两个过期回调引用，调用完成后立即释放。测试接口不能开始游戏、发送普通
游戏按键、写入文件、直接修改浏览器界面状态或强制完成存储同步，所以长流程
仍然通过真实界面执行用户操作。

### 13.2 运行事件记录

阶段四增加一个只保存在当前页面内存中的运行事件记录器，最多保存最近 500 条
记录。第 501 条记录写入时会删除最旧的一条。运行事件包括游戏模块准备、游戏
会话创建、游戏会话退出、回调函数清理、忽略过期回调、存储操作开始、步骤
变化、回滚、提交、启动恢复和错误。

每条运行事件可以包含时间、区域、事件名称、游戏模块编号、游戏会话编号、存储
操作编号、导入事务编号、步骤和数量。运行事件不能包含角色名、正式存档文件
路径、待导入文件名、游戏消息、按键或文件内容。

阶段五会在这套结构上增加跨刷新保存、日志下载、浏览器全局错误捕获和字段过滤
测试。阶段四只实现长流程测试定位错误所需的内存记录，避免同时扩大到完整错误
页面。

## 14. 测试失败时保存什么

每个 Playwright 测试从页面创建开始记录浏览器控制台错误和页面程序错误。测试
失败时，Playwright 保存截图和执行记录。执行记录包含页面导航、点击、键盘
操作和界面变化，开发者可以使用 Playwright 工具逐步查看。

阶段四还会保存三个 JSON 测试结果文件：

```text
runtime-snapshot.json
runtime-events.json
browser-errors.json
```

`runtime-snapshot.json` 保存失败时的应用阶段、游戏模块编号、游戏会话编号、
活动游戏会话数量、回调函数数量、当前存储操作、当前步骤、等待数量和内部文件
数量。`runtime-events.json` 保存最近最多 500 条运行事件。
`browser-errors.json` 保存浏览器控制台错误和页面程序错误。

长流程中的每个断言都会包含当前轮次，例如 `round 4/10`。这样，失败结果可以
直接指出第几轮、哪个游戏会话和哪个存储步骤发生问题。三个 JSON 测试结果文件
遵守与运行事件相同的隐私限制，不包含角色名、文件路径、游戏消息、按键或存档
内容。

## 16. 持续集成和本地测试

持续集成是代码提交后由服务器自动运行构建和测试的流程。普通持续集成每次提交
运行以下命令。`npm` 是 Node.js 项目使用的依赖和脚本管理命令，
`npm run <名称>` 会执行 `package.json` 中对应名称的脚本。代码检查会在不运行
游戏的情况下检查常见代码问题；单元测试检查单个模块；集成测试让多个模块共同
运行，其中浏览器集成测试还会启动真实 Chromium 页面。

```bash
cd frontend
npm run lint
npm test
npm run build
npm run test:integration:wasm
npm run test:integration:browser
```

普通浏览器测试只运行单轮关键流程，执行时间适合每次提交。测试失败时，持续
集成服务器上传截图、执行记录和三个 JSON 测试结果文件。部署任务只有在普通
持续集成通过后才能发布页面。

长流程测试使用 `npm run test:long`。第一版建议把该命令作为本地发布前的强制
步骤，并提供可以手动启动的持续集成任务。长流程稳定运行一段时间、执行时长
明确之后，再决定是否增加每周定时运行。长流程失败时不自动重试，因为自动重试
可能隐藏只能偶尔出现的生命周期错误。

## 17. 人工检查

自动测试通过后，还需要完成以下人工检查：

1. 实际游玩至少 30 分钟，保存、刷新并继续，确认操作、地图和消息历史正常。
2. 手动完成至少 10 次 New Game 或 Continue 与主界面之间的切换，观察加载
   时间是否持续增加。
3. 分别在主界面和游戏界面切换标签页、最小化浏览器并恢复，确认不会重复创建
   游戏模块或游戏会话。
4. 使用测试构建在导入的准备阶段、替换阶段和清理阶段暂停并刷新，确认下一次
   启动结果符合事务记录文件中的阶段。
5. 在浏览器开发者工具中观察回调函数数量、游戏模块生命周期和存储操作等待
   数量，确认这些数量不会持续增加。
6. 检查持久化存储，确认正常流程结束后不存在临时文件、备份文件或事务记录
   文件。

30 分钟游玩只用于人工稳定性观察，不进入自动持续集成，也不要求到达固定地图
位置。

## 18. 实施顺序

阶段四按照以下顺序实现，每一步完成后先运行对应单元测试：

1. 扩展存储测试工具，分开模拟内存文件系统和持久化存储。
2. 实现存储操作协调器、存储操作编号和包含固定字段的错误对象。
3. 把当前导入代码改为明确的导入事务状态，同时保持现有正常导入行为。
4. 增加临时文件、备份文件、事务记录文件、提交点和启动恢复。
5. 完成每个故障注入位置和页面中断位置的 Vitest 测试。
6. 实现容量为 500 条的内存运行事件记录器。
7. 实现只在测试构建中启用的测试接口。
8. 整理现有 Playwright 公共函数，增加失败时的三个 JSON 测试结果文件。
9. 实现三组长流程测试和页面后台测试。
10. 运行代码检查、全部单元测试、生产构建、WebAssembly 集成测试、普通浏览器

## 19. 完成标准

阶段四完成时，以下条件必须全部满足：

1. 所有故障注入位置都有独立、可重复的单元测试。
2. 提交点前的失败能够保持或恢复旧正式存档文件；目标原来不存在时不能产生
   正式存档文件。
3. 标准页面中断能够在下一次启动时自动恢复。
4. 无法安全判断的损坏事务记录文件会让程序停止写入。
5. 游戏会话生命周期重复 10 次通过，任意时刻最多一个活动游戏会话。
6. 同一个存档继续和保存 10 次通过。
7. 导出、删除、导入和继续重复 5 次通过，每轮导入前后的全部字节和 SHA-256
   摘要相同。
8. 过期回调、页面后台恢复、存档列表去重和内部文件清理测试通过。
9. 自动化测试不依赖固定地图、随机怪物行为或固定时间等待。
10. 测试失败结果可以指出循环轮次、游戏会话编号、存储操作编号、导入事务编号
    和失败步骤。
11. 以下命令全部通过：

```bash
cd frontend
npm run lint
npm test
npm run build
npm run test:integration:wasm
npm run test:integration:browser
npm run test:long
```

## 20. 实现前需要确认的五项决定

第一项决定是持久化备份文件。本文建议在导入期间同时使用内存副本和 `.bak`
备份文件。内存副本用于当前页面内的快速回滚，备份文件用于页面刷新后的启动
恢复。缺少备份文件时，页面刷新会销毁唯一的旧内容副本，因此无法可靠满足阶段
四的恢复要求。

第二项决定是四次存储同步。本文建议依次保存恢复材料、保存新正式存档、保存
提交决定、保存清理结果。四次存储同步会增加一次导入所需时间，但每一步都有
明确作用，并且启动恢复可以根据已准备阶段或已提交阶段作出确定决定。

第三项决定是测试接口。本文建议只在 `VITE_ENABLE_TEST_API=1` 的测试构建中
启用测试接口，公开部署不包含该接口。长流程测试依靠该接口验证活动游戏会话、
回调函数和存储操作数量，同时仍然通过真实界面执行游戏操作。

第四项决定是阶段四的运行事件记录。本文建议阶段四先实现只保存在当前页面
内存、容量为 500 条的运行事件记录器。阶段五在相同数据结构上增加跨刷新保存、
日志下载和浏览器全局错误捕获。

第五项决定是长流程测试的持续集成频率。本文建议阶段四先提供本地强制命令和
手动启动的持续集成任务，不在每次提交时运行长流程。普通测试仍然在每次提交时
运行。团队观察长流程的执行时间和稳定性后，再决定是否增加每周定时任务。
