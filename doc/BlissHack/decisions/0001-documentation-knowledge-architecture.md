# ADR-0001：文档知识架构

- **状态**：Accepted
- **日期**：2026-10-27
- **决策者**：BlissHack maintainers

## 背景

BlissHack 的版本计划、阶段设计、验收记录、当前架构和 Agent 启动说明长期放在
同一目录。随着版本推进，同一事实开始同时出现在 README、`session-start.md`、
计划和验收记录中。历史内容仍有审计价值，但不应继续作为当前开发的默认上下文。

MCP 可以为 Agent 提供统一的资源和工具接口，但它只解决访问问题。如果底层内容
没有权威来源和生命周期，MCP 只会更快地返回重复或过期信息。

## 决策

BlissHack 文档分为四层：

1. `current/` 保存当前有效的状态和架构。
2. `decisions/` 保存不可变的架构决策记录；新决定通过 `Superseded` 关系取代
   旧决定。
3. `releases/` 保存完成版本的计划、设计评审、验收记录和发布证据。
4. `index.md`、README 和 `session-start.md` 只做面向不同读者的入口和路由。

`VERSION` 与 `releases/manifest.json` 是发布状态的机器权威来源。
`current/status.md` 和 `releases/index.md` 从它们生成，不手工维护。
`knowledge-map.json` 声明当前活跃文档和入口。CI 校验版本一致性、清单路径、
旧目录引用、本地 Markdown 链接和生成文件漂移。

本阶段不引入 MCP server 或向量数据库。未来若需要 MCP，它只能读取上述权威
来源，并默认排除 `releases/` 历史内容；MCP 不能成为新的事实副本。

## 后果

- 默认上下文显著缩小，当前事实与历史过程不再混用。
- 版本历史完整保留，调查回归和设计来源时仍可追溯。
- 新增文档必须先判断属于当前事实、决策还是发布历史。
- 发布清单和生成脚本成为新的维护面，但其一致性由自动测试保证。
- 旧外部深链在目录迁移后需要更新；仓库内链接由健康检查保护。
