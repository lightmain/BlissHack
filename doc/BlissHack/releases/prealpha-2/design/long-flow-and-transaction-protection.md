# BlissHack 阶段四：长流程测试与导入失败路径测试设计

本文定义 prealpha-2 阶段四的简化方案。阶段四主要增加长流程自动化测试和
持续集成，同时补充当前存档导入代码的失败路径单元测试。阶段四不会增加
持久化备份文件、事务记录文件、跨刷新恢复协议、导入状态机、生产环境故障注入
框架或全局测试接口。

这个范围建立在当前 IDBFS 实现和当前导入代码已经提供的保护上。本文先说明
这些保护能够处理哪些情况，再说明仍然需要补充哪些测试。

## 1. 阶段四的两个目标

第一个目标是重复执行已经实现的用户流程。一次新游戏、保存或导入成功，不能
证明程序在第十次创建游戏模块后仍然正确。长流程测试会反复创建和清理游戏
会话，反复从持久化存储读取存档，并反复执行导出、删除和导入。

第二个目标是验证当前导入代码遇到普通错误时能够回滚。这里的“普通错误”表示
JavaScript 程序仍然运行并收到明确错误，例如写入文件失败、文件改名失败或
`syncfs(false)` 返回错误。单元测试会直接让现有文件系统测试替身在指定调用
处返回错误，不会在生产代码中增加专门的故障注入接口。

## 2. 当前存档写入怎样工作

### 2.1 内存文件系统和持久化存储

BlissHack 使用 Emscripten 把 NetHack 的 C 程序编译成 WebAssembly。
Emscripten 是一套把 C 或 C++ 程序编译到浏览器环境的工具链。Emscripten
还向 NetHack 提供位于浏览器内存中的文件系统。本文把该文件系统称为“内存
文件系统”。

页面刷新会销毁当前页面的内存。为了让存档跨刷新保留，Emscripten 使用
IDBFS（IndexedDB File System）在内存文件系统和浏览器 IndexedDB 数据库之间
复制文件。本文把 IndexedDB 中由 IDBFS 管理的数据称为“持久化存储”。

IDBFS 通过 `syncfs` 函数执行复制。本文把一次 `syncfs` 调用称为“存储同步”：

1. `syncfs(true)` 从持久化存储读取文件，并把文件放入当前游戏模块的内存文件
   系统。程序在显示主界面之前执行这个方向的存储同步。
2. `syncfs(false)` 从内存文件系统读取文件，并把文件写入持久化存储。程序在
   保存、删除或导入之后执行这个方向的存储同步。

### 2.2 一次存储同步使用一个 IndexedDB 写入事务

当前生成的 `frontend/public/nethack.js` 中，IDBFS 在执行
`syncfs(false)` 时创建一个 IndexedDB 写入事务。这里的“IndexedDB 写入事务”
表示 IndexedDB 把本次存储同步涉及的新增、修改和删除作为一组操作处理：整组
操作提交后全部生效；写入事务取消后整组操作都不生效。

IDBFS 只在 IndexedDB 写入事务触发完成事件后报告存储同步成功。IndexedDB
写入事务发生错误或被取消时，IDBFS 报告存储同步失败。因此，应用代码不需要
通过额外的事务记录文件实现同一层保护。

### 2.3 当前导入流程

正式存档文件位于 `/save/0<角色名>`。NetHack 写入的是二进制文件，导入和
导出不会把文件转换成 JSON 或其他 BlissHack 格式。

当前导入流程已经执行以下步骤：

1. 检查待导入文件不为空，并且不超过 64 MiB。MiB 是以
   1024 × 1024 字节计算的容量单位。
2. 使用当前构建提供的存档格式指纹和角色身份信息校验待导入内容。
3. 如果同名正式存档已经存在并且玩家尚未确认覆盖，停止写入并显示冲突确认。
4. 玩家确认覆盖后，把旧正式存档的全部字节复制到 JavaScript 内存。
5. 把待导入内容写入随机命名的 `.tmp` 临时文件。
6. 读回临时文件，确认读回内容与待导入内容逐字节相同。
7. 把临时文件改名为正式存档文件。
8. 执行一次 `syncfs(false)`。
9. 如果步骤 5 至 8 返回错误，删除临时文件，使用内存中的旧字节恢复正式存档，
   然后再次执行 `syncfs(false)` 保存回滚结果。

步骤 5、6 和 7 都是同步执行的 JavaScript 调用。这三个步骤执行期间，浏览器
不会在同一个页面中插入另一个 JavaScript 任务。程序到达第一个异步等待点时，
临时文件已经改名为正式存档文件。因此，正常导入不会通过存储同步把临时文件
写入持久化存储。

## 3. 页面中断时可能出现什么结果

下面使用 A 表示旧正式存档的完整字节，使用 B 表示玩家确认覆盖的新存档完整
字节。

页面在 `syncfs(false)` 开始前关闭时，内存文件系统中的变化尚未写入持久化
存储。下一次打开页面后，程序从持久化存储读到 A。

页面在 `syncfs(false)` 执行期间关闭时，IndexedDB 写入事务可能尚未提交，也
可能已经提交。尚未提交时，下一次打开页面后读到 A；已经提交时，下一次打开
页面后读到 B。由于一次存储同步使用一个 IndexedDB 写入事务，程序不应读到
只包含一部分 B 的正式存档。

页面在存储同步提交之后、界面显示导入成功之前关闭时，下一次打开页面后会读到
B。玩家无法从关闭前的界面确认导入是否成功，但 B 是经过临时文件读回校验的
完整文件。这是操作结果提示上的不确定性，不是存档内容损坏。

阶段四接受上述结果。页面在极短的导入同步期间中断后，应用可以保留完整 A 或
完整 B。阶段四只要求重新打开应用后，正式存档能够通过存档列表校验并继续
游戏。阶段四不保证页面中断后一定选择 A，也不保证一定选择 B。

## 4. 明确删除的设计内容

阶段四不实现以下内容：

- `.bak` 持久化备份文件；
- `.journal` 事务记录文件；
- 四次存储同步协议；
- 导入事务编号和存储操作编号；
- 导入事务状态机；
- 页面启动时扫描和恢复未完成导入；
- 生产代码中的故障注入检查点；
- 为长流程测试增加的全局浏览器测试接口；
- 提前实现阶段五的运行事件记录和诊断日志；
- 为导入测试建立两套复杂的内存与持久化文件快照模型。

这些内容会增加生产代码路径、错误状态、文件格式和维护成本。当前 IDBFS 写入
事务、临时文件校验和内存回滚已经覆盖阶段四需要的主要风险。

## 5. 保留的导入保护

阶段四保留阶段三已经实现的导入方式，不重写 `storage-transaction.ts` 的主体
流程。保留的行为包括：

1. 上传文件名不决定目标角色，目标角色来自存档内部身份信息。
2. 无效、空白和过大的待导入文件在写入前被拒绝。
3. 同名覆盖需要玩家明确确认。
4. 新内容先写入临时文件并读回比较。
5. 临时文件通过比较后才改名为正式存档文件。
6. 已有正式存档在覆盖前复制到 JavaScript 内存。
7. 第一次存储同步明确失败时，程序恢复旧字节并再次同步。
8. 导入新角色失败时，程序删除导入过程中产生的正式存档文件。
9. 导入成功后重新扫描正式存档列表。

阶段四不会为了测试改变这些产品行为。只有单元测试发现现有回滚存在明确缺陷
时，才对对应函数做局部修复。

## 6. 导入失败路径单元测试

Vitest 是本项目运行 TypeScript 单元测试的工具。现有测试使用可控制的内存
文件系统替身，并允许测试决定每次 `syncfs` 何时成功或失败。阶段四继续使用
这套测试工具，通过替换具体文件系统方法的返回结果覆盖失败路径。

### 6.1 待读取和校验失败

组件测试覆盖浏览器读取待导入文件失败。测试确认界面显示 Import failed，
文件系统没有新增临时文件或正式存档文件。

存储服务测试覆盖待导入内容没有通过存档校验。测试确认校验失败发生在任何文件
写入之前，已有正式存档保持不变。

### 6.2 写入临时文件失败

测试让 `writeFile()` 在写入临时文件时抛出错误。目标原来存在正式存档时，
正式存档全部字节保持不变；目标原来不存在时，不产生正式存档文件。测试还确认
错误返回给调用方。

### 6.3 读回内容不一致

测试让 `readFile()` 返回与刚写入内容不同的字节。导入函数必须把这种情况视为
临时文件校验失败，删除临时文件，恢复已有正式存档，并保存回滚结果。

### 6.4 文件改名失败

测试让 `rename()` 抛出错误。导入函数必须删除仍然存在的临时文件，保持或恢复
原正式存档，然后执行存储同步保存清理和回滚结果。

### 6.5 第一次存储同步失败

现有测试已经覆盖第一次 `syncfs(false)` 失败的主要路径。覆盖已有正式存档时，
导入函数把内存文件系统中的正式存档恢复为旧字节，并执行第二次
`syncfs(false)`。导入新角色时，导入函数删除新正式存档，并执行第二次
`syncfs(false)`。

阶段四补充断言，确认临时文件已经消失、正式存档内容正确，并且界面没有显示
导入成功。

### 6.6 回滚存储同步失败

测试让第一次和第二次 `syncfs(false)` 都失败。导入函数应返回同时包含导入
错误和回滚错误的 `AggregateError`。`AggregateError` 是 JavaScript 用来把
多个相关错误放在同一个错误对象中的标准类型。

测试只能确认当前内存文件系统中的旧字节已经恢复。第二次存储同步失败意味着
应用无法证明回滚结果已经写入持久化存储，所以界面不能显示成功。阶段五会为
这类无法继续确认的错误提供完整错误页面和诊断日志。

### 6.7 单元测试完成标准

每个测试都检查：

- 正式存档文件的最终字节；
- 临时文件是否存在；
- 存储同步调用次数和顺序；
- 成功或错误结果；
- 已有存档是否被意外删除。

测试不会检查导入事务编号、事务状态或跨刷新恢复，因为阶段四不再引入这些
概念。

## 7. 长流程浏览器测试

Playwright 是本项目控制真实 Chromium 浏览器的自动化测试工具。Chromium 是
Chrome 浏览器所基于的开源浏览器内核。长流程浏览器测试使用真实
WebAssembly、浏览器界面和 IndexedDB。

阶段四增加独立命令：

```bash
cd frontend
npm run test:long
```

普通浏览器测试继续验证单次关键流程。长流程测试反复执行相同流程，用来发现
游戏模块没有释放、回调函数没有清理、存档列表重复和多轮同步后存档丢失等问题。

长流程测试不使用固定时间等待。测试等待可观察的界面条件或浏览器事件，例如
主界面出现、地图出现、存档项目出现和下载完成。这个约束可以减少不同机器运行
速度造成的测试失败。

### 7.1 游戏会话生命周期重复 10 次

每一轮执行：

1. 从主界面点击 New Game。
2. 等待名字输入并输入本轮使用的唯一名字。
3. 等待随机角色选择问题。
4. 按 `q` 使用 NetHack 正常退出路径。
5. 等待主界面重新出现。
6. 断言游戏界面、名字输入和旧地图已经消失。

角色选择阶段已经调用 NetHack 的 `main()` 并建立游戏会话，因此这个流程能够
验证游戏模块创建、游戏会话创建、核心退出、回调函数清理和下一游戏模块创建。
该流程不依赖随机地图。

现有 session manager 单元测试继续直接验证一次只能创建一个游戏会话、每个
游戏模块只调用一次 `main()`、过期回调不影响下一局以及清理具有幂等性。幂等性
表示同一个清理操作执行多次与执行一次具有相同结果。长流程浏览器测试不增加
全局测试接口来重复读取这些内部状态。

### 7.2 同一个存档继续和保存 10 次

测试先创建一个角色并保存。随后重复以下流程 10 次：

1. 刷新页面并等待主界面。
2. 打开存档列表，确认目标角色只出现一次。
3. 点击 Continue。
4. 确认名字输入和角色创建问题没有出现。
5. 确认地图和角色状态可见。
6. 使用 NetHack 的 `S` 命令和确认问题完成保存。
7. 等待主界面重新出现。

测试不要求角色移动，因为可移动方向取决于随机地图。继续和保存流程已经覆盖
游戏模块替换、正式存档消费、正式存档重新创建和 IDBFS 存储同步。

### 7.3 导出、删除、导入和继续重复 5 次

每一轮执行：

1. 从存档列表导出正式存档。
2. 保存下载文件的全部字节，并计算 SHA-256 摘要。SHA-256 摘要是根据全部
   文件字节计算出的固定长度数值；相同字节会产生相同摘要。
3. 完成二次删除确认。
4. 使用真实浏览器文件选择器导入刚导出的文件。
5. 再次导出，比较两次文件的全部字节和 SHA-256 摘要。
6. Continue 并确认 NetHack 恢复原角色。
7. 再次保存，为下一轮产生正式存档文件。

同一轮导入前后的全部字节必须相同。角色继续游戏并再次保存后，游戏时间和其他
内部状态可能改变，因此不同轮次之间不比较 SHA-256 摘要。

### 7.4 页面进入后台和重复扫描

测试在主界面打开另一个浏览器页面，使 BlissHack 页面进入后台，然后返回
BlissHack 页面。主界面不应变成游戏界面，也不应出现重复名字输入。

测试还会反复打开和关闭存档列表，并通过页面刷新触发新的游戏模块读取持久化
存储。每次显示的角色项目数量保持一致，不出现重复项目。

### 7.5 错误收集

每个长流程测试从页面创建开始收集：

- 浏览器控制台中的 error 级别消息；
- 页面程序抛出的未处理错误；
- 下载失败；
- 失败时的 Playwright trace；
- 失败时的截图。

Playwright trace 是 Playwright 保存的测试执行记录，其中包含页面导航、点击、
键盘操作和界面变化。测试断言会注明当前循环轮次，例如 `round 4/10`，从而让
失败结果指出发生问题的轮次。

阶段四不提前实现阶段五诊断日志，也不新增只供浏览器测试使用的生产代码接口。

## 8. Playwright 文件组织

预计增加：

```text
frontend/playwright.long.config.ts
frontend/test/integration-tests/browser-long/long-flow.spec.ts
```

可以从现有 `playable-frontend.spec.ts` 提取以下公共测试函数：

```text
frontend/test/integration-tests/browser/helpers/game-flow.ts
frontend/test/integration-tests/browser/helpers/browser-errors.ts
```

`game-flow.ts` 包含通过真实界面开始游戏、保存并返回主界面、选择存档继续和
导入导出等操作。`browser-errors.ts` 负责收集浏览器控制台错误和页面程序错误。
这些文件只属于测试代码，不会进入公开部署的前端代码。

普通 Playwright 配置和长流程配置使用不同端口和不同测试结果目录。长流程使用
一个 Chromium worker。worker 是 Playwright 同时运行测试的执行进程；设置为
一个可以避免多个长流程同时访问相同浏览器存储。

## 9. 持续集成

持续集成是代码提交后由服务器自动运行构建和测试的流程。普通持续集成运行：

```bash
cd frontend
npm run lint
npm test
npm run build
npm run test:integration:wasm
npm run test:integration:browser
```

普通持续集成覆盖代码检查、单元测试、生产构建、WebAssembly 集成测试和单轮
浏览器流程。普通持续集成适合每次提交运行。

长流程测试使用：

```bash
cd frontend
npm run test:long
```

第一版把长流程测试作为本地发布前检查，并提供手动启动的持续集成任务。观察
执行时间和稳定性之后，再决定是否增加每周定时任务。长流程失败不自动重试，
因为重试可能隐藏偶尔出现的生命周期错误。

## 14. 已接受的风险

玩家确认覆盖后，如果页面恰好在导入存储同步期间关闭，重新打开页面时可能保留
旧存档，也可能保留新存档。应用不保证选择其中某一个版本。应用保证正常 IDBFS
行为下不会产生只写入一部分的新正式存档。

这个取舍适用于当前项目的条件：单个标签页、单个玩家、低频手动导入、较小存档
以及 pre-alpha 阶段。以后如果项目增加跨标签页并发写入、云同步、大型文件或
后台自动导入，需要重新评估持久化事务协议。
